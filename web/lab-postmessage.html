Lab: window.postMessage → privileged extension actions

This lab shows how a webpage can end up triggering privileged extension behavior through an unsafe message bridge.

Before you start
1) Start the local server: cd dvce/web && python3 -m http.server 8000
2) Load the extension from dvce/extension
3) Open the DVCE popup and set Mode to vulnerable (then refresh this page)

What you are sending (this page)

When you click a button, this page sends a message to its own window:

window.postMessage({ dvce: true, id, cmd, args }, "*");
Why postMessage?
Content scripts run in an “isolated world” and can’t directly call functions/variables in the page’s JavaScript. Many extensions use window.postMessage as a bridge between page JS ↔ content script.

In a real application, this message could be sent by:

  • the site’s own JavaScript
  • a third-party script loaded by the site (analytics, ads, tag managers)
  • an XSS payload on the site
  • a cross-origin iframe using parent.postMessage (see the iframe lab)

What runs inside the extension

0) Manifest: dvce/extension/manifest.json
The manifest tells Chrome which scripts to run and on which pages.
Show the relevant manifest snippet 
"background": { "service_worker": "sw.js" },
"content_scripts": [
  {
    "matches": ["http://localhost/*", "http://127.0.0.1/*"],
    "js": ["content.js"]
  }
]
1) Content script: dvce/extension/content.js
A content script is JavaScript that Chrome injects into matching webpages (configured in manifest.json). It can read/modify the page DOM and it can message the extension service worker.
Show the snippet this lab hits 
window.addEventListener("message", (event) => {
  const data = event?.data;
  if (!data || data.dvce !== true) return;
  if (data.type === "DVCE_RESPONSE") return;

  // Fixed mode: validates the sender (origin + window).
  // Note: the service worker (sw.js) must still authorize commands.
  if (currentMode === "fixed") {
    if (event.source !== window) return;
    if (!isAllowedLocalOrigin(event.origin)) return;
  }

  // Vulnerable mode: no origin/source checks; forwards commands.
  chrome.runtime.sendMessage(
    { type: "DVCE_CMD", cmd: data.cmd, args: data.args },
    (response) => window.postMessage({ dvce: true, type: "DVCE_RESPONSE", id: data.id, response }, "*")
  );
});
2) Service worker: dvce/extension/sw.js
The service worker (background) is where extensions typically perform privileged actions using chrome.* APIs (tabs, scripting, storage, etc.).
Show the snippet this lab hits 
chrome.runtime.onMessage.addListener((message, sender, sendResponse) => {
  if (message.type !== "DVCE_CMD") return;

  // Fixed mode blocks unknown senders and commands.
  // Vulnerable mode executes based on cmd + args.

  if (message.cmd === "setBadge") {
    chrome.action.setBadgeText({ tabId: sender.tab.id, text: message.args.text });
  }

  if (message.cmd === "openTab") {
    chrome.tabs.create({ url: message.args.url });
  }

  if (message.cmd === "injectTitle") {
    chrome.scripting.executeScript({
      target: { tabId: sender.tab.id },
      func: (title) => (document.title = title),
      args: [message.args.title]
    });
  }
});

Flow (why this becomes a vulnerability)

Web page JS
  └─ window.postMessage({ cmd: ... })
        └─ Content script (content.js) listens and forwards
              └─ chrome.runtime.sendMessage({ cmd: ... })
                    └─ Service worker (sw.js) performs privileged actions

Real-world implications

    
    
      
  • Confused deputy: a site can “borrow” the extension’s privileges.
    • 
      
  • 
        If the extension has broad host access/permissions, an attacker-controlled message can drive actions like tab
        navigation, script injection, or sensitive data access (depending on what the extension exposes).
      
    • 
      
  • 
        Even with an origin allowlist, a site-level XSS (or malicious third-party script) can still send messages because it
        runs on the allowed origin.
      
    • 
    


    
How to secure (what DVCE fixed mode demonstrates)

    
    
      
  • Validate the sender: check event.source and allowlist event.origin.
    • 
      
  • Validate the message: strict schema + strict command allowlist (never “do whatever cmd says”).
    • 
      
  • Enforce in the background: sw.js must re-check sender.tab.url and allowed commands.
    • 
      
  • Minimize access: reduce permissions and host matches (avoid <all_urls> unless essential).
