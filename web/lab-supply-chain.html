Lab: Supply chain & dependency attacks

Most extensions depend on third-party code (npm packages, bundled libraries, build tooling). A supply-chain compromise can turn a trusted extension update into a mass infection.

Key idea
A dependency is code that runs with the same privileges as your extension. If it’s compromised, users inherit that compromise automatically via updates.

Common real-world supply-chain paths

  • Compromised npm package / maintainer account takeover
  • Typosquatting / dependency confusion
  • CI/CD compromise (build artifacts tampered before publishing)
  • Publisher account takeover (malicious update pushed to users)

What “bad” looks like in code

Examples of risky patterns (even if they look “convenient”):

// Pulling behavior from outside the reviewed extension package
fetch("https://config.example.com/extension.json").then(r => r.json())

// Executing strings as code (never do this)
eval(untrustedString)

How to secure

  • Minimize dependencies; prefer small, well-audited libraries.
  • Pin versions with lockfiles; review diffs on updates.
  • Generate an SBOM and run SCA scanning (Snyk, osv-scanner, etc.).
  • Harden publishing: MFA, least-privileged access, protected branches, signed releases.
  • Monitor for anomalous extension behavior after release (telemetry with privacy in mind).
