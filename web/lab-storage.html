Lab: Insecure Storage of Sensitive Data

This lab demonstrates a common risk: extensions storing secrets (tokens, API keys, session data) in chrome.storage in plain text.

Why this matters
If your extension is ever compromised (extension-page XSS, unsafe message bridge, supply-chain update), an attacker can read anything you stored and steal accounts/data.
DVCE Mode note
DVCE fixed mode intentionally blocks these “store/read secret” commands from webpages. Use vulnerable mode for this demo.

Hands-on: store a fake token

This page sends commands to DVCE to write/read a value from chrome.storage.sync.

Show the storage call (service worker) 
chrome.storage.sync.set({ dvceSecret: token });
chrome.storage.sync.get({ dvceSecret: null }, (r) => r.dvceSecret);
Safety
Use a fake value here. Do not paste a real password or real token. 


    
Real-world implications

    
    
      
  • Stolen API keys → abuse of your backend services and billing.
    • 
      
  • Stolen user tokens/cookies → account takeover.
    • 
      
  • Stolen internal data → compliance and incident response impact.
    • 
    


    
How to secure

    
    
      
  • Don’t store long-lived secrets in extensions unless absolutely required.
    • 
      
  • Prefer short-lived tokens and rotate them often.
    • 
      
  • Never expose “read secret” functionality to webpages (only to trusted extension UI).
    • 
      
  • Assume the extension package is public; protect server-side with real authZ.
