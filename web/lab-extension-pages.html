Lab: XSS / HTML injection in extension pages

Extension pages (like popup.html and options.html) run under chrome-extension://<extension-id>/... and can call powerful chrome.* APIs.

Why this is severe
If an attacker gets JavaScript execution in an extension page, they effectively get “extension-level” privileges (whatever permissions the extension has). That can be much worse than normal website XSS.

What you will do

  1. Set DVCE Mode to vulnerable (DVCE popup → Toggle if needed)
  2. Send a message from this webpage to the DVCE content script
  3. DVCE forwards it to the service worker, which opens options.html with ?dvceMsg=...
  4. Observe how unsafe rendering in an extension page becomes high impact
Why you saw ERR_BLOCKED_BY_CLIENT
Chrome blocks websites from directly opening most chrome-extension:// pages unless the extension explicitly exposes them (e.g., via web_accessible_resources) or the extension itself opens them. This is a safety barrier.

This lab demonstrates a realistic bypass: a vulnerable extension can be tricked (via unsafe messaging) into opening its own privileged page with attacker-controlled input.
Troubleshooting
If you see chrome.runtime.sendMessage errors or get “(no response)”, confirm:
  • DVCE is loaded at chrome://extensions (and reloaded after code changes)
  • You opened this lab as http://localhost:8000/... (DVCE only matches localhost)

What gets triggered inside the extension

    

      1) Content script: dvce/extension/content.js

      Content scripts run inside matching webpages. DVCE listens to window.postMessage and forwards the command to the
      service worker via chrome.runtime.sendMessage.
      

        Show the relevant snippet (content.js)
        
window.addEventListener("message", (event) => {
  const data = event?.data;
  if (!data || data.dvce !== true) return;
  if (data.type === "DVCE_RESPONSE") return;

  // Vulnerable mode: forwards page-controlled cmd + args
  chrome.runtime.sendMessage(
    { type: "DVCE_CMD", cmd: data.cmd, args: data.args },
    (response) => window.postMessage({ dvce: true, type: "DVCE_RESPONSE", response }, "*")
  );
});

      

    


    

      2) Service worker: dvce/extension/sw.js

      The service worker can use privileged APIs. For this lab it opens DVCE’s options.html with a query parameter.
      

        Show the relevant snippet (sw.js)
        
if (cmd === "openOptionsWithMsg") {
  const url = new URL(chrome.runtime.getURL("options.html"));
  url.searchParams.set("dvceMsg", args.msg);
  await chrome.tabs.create({ url: url.toString() });
  sendResponse({ ok: true });
}

      

    


    
Where the vulnerable code lives

    

      The opened extension page is dvce/extension/options.html. Its script (options.js) reads
      ?dvceMsg=... and renders it. In vulnerable mode it uses innerHTML.
    

    

      Show the key pattern
      
// Vulnerable (HTML injection)
el.innerHTML = dvceMsg;

// Fixed (safe text rendering)
el.textContent = dvceMsg;

    


    
How to secure

    
    
      
  • Treat extension pages like admin panels: never render untrusted HTML.
    • 
      
  • Use safe sinks (textContent) and strict sanitization only when absolutely required.
    • 
      
  • Keep extension CSP strict (avoid 'unsafe-inline', 'unsafe-eval').
    • 
      
  • Minimize permissions so impact is limited even if a bug exists.
    • 
      
  • Lock down messaging: allowlist origins/commands and re-check in the service worker.
