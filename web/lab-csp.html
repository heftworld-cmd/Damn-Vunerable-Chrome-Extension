Lab: Content Security Policy (CSP) for extensions

CSP is one of the most important controls for Chrome extensions because extension pages are privileged. A weak CSP can make injection bugs (XSS/HTML injection) much easier to turn into full extension takeover.

Key idea
Website XSS runs with website privileges. Extension page XSS runs with extension privileges (whatever permissions the extension has). CSP helps prevent risky script execution patterns like inline scripts and eval.

What “bad” looks like

Examples of CSP values that drastically increase risk:

// Dangerous patterns (don’t do this)
script-src 'self' 'unsafe-inline' 'unsafe-eval'
  • 'unsafe-inline' allows inline scripts and inline event handlers to execute.
  • 'unsafe-eval' allows dynamic code execution via eval() / new Function().

How Chrome MV3 helps (and how devs still shoot themselves)

  • MV3 pushes extensions toward stricter CSP and blocks many remote-code patterns.
  • But developers can still build “remote behavior” via dangerous config interpreters, overly broad permissions, or unsafe messaging.

How to secure

  • Keep CSP strict. Avoid 'unsafe-inline' and 'unsafe-eval'.
  • Never execute strings as code. Don’t build “mini interpreters” from JSON.
  • Use safe DOM APIs (textContent) and treat all external input as untrusted.
  • Minimize permissions so the worst-case impact is smaller.
