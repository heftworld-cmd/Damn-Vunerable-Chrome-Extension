Lab: Remote config → privileged actions

Chrome MV3 tries to prevent remote code execution (loading arbitrary scripts from the internet). But extensions can still build dangerous behavior by fetching a “remote config” and interpreting it as commands.

Key idea
If your extension fetches config from a server and the config can “tell the extension what to do”, then compromise of that config channel can become compromise of the extension’s behavior.
DVCE Mode note
DVCE fixed mode is designed to block high-risk commands like applyRemoteConfig. Use vulnerable mode for this demo.

What this lab does

This page asks DVCE to fetch a JSON file (served by your local server) and then execute actions described in that JSON.

Show the request this page sends 
window.postMessage(
  { dvce: true, cmd: "applyRemoteConfig", args: { url: "http://localhost:8000/remote-config-safe.json" } },
  "*"
);

What gets triggered inside the extension

1) Content script: dvce/extension/content.js
Chrome injects content.js into this page (because of matches in the manifest). It listens for window.postMessage and forwards the command to the extension service worker via chrome.runtime.sendMessage.
Show the relevant snippet (content.js) 
window.addEventListener("message", (event) => {
  const data = event?.data;
  if (!data || data.dvce !== true) return;
  if (data.type === "DVCE_RESPONSE") return;

  // Fixed mode: validate sender (origin/source).
  // Command allowlisting is enforced in the service worker (sw.js).
  if (currentMode === "fixed") {
    if (event.source !== window) return;
    if (!isAllowedLocalOrigin(event.origin)) return;
  }

  // Vulnerable mode: forwards page-controlled cmd + args
  chrome.runtime.sendMessage(
    { type: "DVCE_CMD", cmd: data.cmd, args: data.args },
    (response) => window.postMessage({ dvce: true, type: "DVCE_RESPONSE", response }, "*")
  );
});
2) Service worker: dvce/extension/sw.js
The service worker receives the forwarded command and performs privileged actions (network fetch, tabs, scripting).
Show the high-level flow (sw.js) 
chrome.runtime.onMessage.addListener(async (message, sender, sendResponse) => {
  if (message.type !== "DVCE_CMD") return;
  const cmd = message.cmd;
  const args = message.args;

  // Fixed mode blocks risky commands like applyRemoteConfig
  if (mode === "fixed") {
    const allowedCmds = new Set(["setBadge", "openTabLocal", "injectTitle", "getManifestInfo", "getActiveTab"]);
    if (!allowedCmds.has(cmd)) return sendResponse({ ok: false, error: "blocked_cmd" });
  }

  if (cmd === "applyRemoteConfig") {
    const resp = await fetch(args.url);
    const config = await resp.json();
    for (const action of config.actions) {
      // Executes actions like setBadge / injectTitle / openTab / openTabLocal
    }
    return sendResponse({ ok: true });
  }
});

What the config JSON looks like

The config is just data, but it can still become dangerous if your extension treats it as a list of “commands to run”.

Show example config (remote-config-safe.json) 
{
  "name": "safe",
  "actions": [
    { "cmd": "setBadge", "args": { "text": "CFG" } },
    { "cmd": "injectTitle", "args": { "title": "DVCE: config applied (safe)" } },
    { "cmd": "openTabLocal", "args": { "url": "http://localhost:8000/" } }
  ]
}

Real-world implications

    
    
      
  • “Remote config” can become a remote command channel if you don’t validate it strictly.
    • 
      
  • Even if you never load remote JS, config can still trigger high-impact extension actions.
    • 
      
  • If the config is hosted on a CDN or third-party service, that supply chain becomes your security boundary.
    • 
    


    
How to secure

    
    
      
  • Keep config data-only (feature flags), never “run arbitrary actions”.
    • 
      
  • Use strict schema validation + allowlists for every config field.
    • 
      
  • Pin config sources (allowlist domains) and use integrity/authentication where possible.
    • 
      
  • Prefer local/static config baked into the extension when feasible.
