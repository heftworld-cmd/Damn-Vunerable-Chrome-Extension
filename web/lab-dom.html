Lab: content script DOM injection

Goal
Understand how a content script can accidentally introduce XSS into a webpage by using dangerous DOM sinks like innerHTML.

DVCE’s content script reads ?dvceBanner=... and renders it into the page. In vulnerable mode it uses innerHTML (unsafe). In fixed mode it uses textContent (safe).

Where this happens in the extension

The code is in dvce/extension/content.js. It builds a banner and renders the query parameter into it.

Show the key snippet (content.js) 
// Fixed mode (safe)
body.textContent = bannerParam;

// Vulnerable mode (unsafe)
body.innerHTML = bannerParam;

Try it

  1. Set DVCE mode to vulnerable and refresh this page.
  2. Click Apply with the default value: <b>Hello from HTML</b>.
  3. Notice the banner shows bold text (HTML was interpreted).
  4. Toggle DVCE mode to fixed, refresh, and click Apply again.
  5. Now the banner shows the literal text (HTML is not interpreted).


    

    
Real-world implications

    
    
      
  • 
        If an attacker can influence the input (URL params, DOM text, API responses) and you render it with
        innerHTML, you can create script execution in the website’s context.
      
    • 
      
  • 
        That can lead to session theft, phishing overlays, form tampering, or data exfiltration on the affected site—even if
        the extension itself isn’t “hacked”.
      
    • 
    


    
How to secure

    
    
      
  • Prefer textContent for untrusted data.
    • 
      
  • If you must render HTML, use strict allowlisted templates or a well-reviewed sanitizer.
    • 
      
  • Minimize the pages your content scripts run on (host matches) to reduce blast radius.
