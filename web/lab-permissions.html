Lab: Excessive Permissions (Over‑privileged extensions)

This lab explains why requesting broad permissions like tabs, cookies, <all_urls>, or webRequest can turn a single extension bug into a browser-wide incident.

Key idea
Permissions are the blast radius. If an extension is compromised (XSS in extension pages, supply-chain update, unsafe message bridge), an attacker inherits all granted permissions.

Where permissions live

Chrome extension capabilities are declared in dvce/extension/manifest.json:

Show example snippet 
{
  "permissions": ["tabs", "cookies", "webRequest"],
  "host_permissions": ["<all_urls>"]
}
Two important buckets
1) permissions — powerful APIs (tabs, cookies, webRequest, scripting, …)
2) host_permissions — which websites the extension can access (https://*.example.com/*, <all_urls>, …)

Hands-on: ask DVCE what it requested

This page sends a DVCE command via window.postMessage. The extension’s content script (content.js) forwards it to the service worker (sw.js), which replies with manifest info.

Show the request this page sends 
window.postMessage({ dvce: true, cmd: "getManifestInfo" }, "*");


    
Why these specific permissions are high-impact

    
    
      
  • tabs: can reveal where users browse (URLs, titles) and enable tab manipulation.
    • 
      
  • cookies: can expose session cookies (account takeover risk).
    • 
      
  • <all_urls>: makes the extension run “everywhere”, multiplying exposure and data access.
    • 
      
  • webRequest: can observe (and sometimes influence) network traffic.
    • 
    


    
Real-world implications

    
    
      
  • Data theft: browsing history/URLs, form data, tokens (depends on permissions/features).
    • 
      
  • Session hijacking: if cookies or auth headers are accessible.
    • 
      
  • Stealth spying: background tracking via tab/network events.
    • 
    


    
How to secure

    
    
      
  • Request the minimum permissions required for the feature.
    • 
      
  • Prefer narrow host permissions over <all_urls>.
    • 
      
  • Use optional permissions and ask only when needed.
    • 
      
  • Review permissions during code review like you review authentication/authorization.
